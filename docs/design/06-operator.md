# 06 · Operator Interfaces

## 1. Operator layer

CLI, MCP and the dashboard palette are thin adapters over three small services:

| Service | Responsibility |
|---|---|
| `OperatorQueries` | Read-only views over `StateReader`: status, tasks, task detail, bounded task evidence pages across SQL events and recorded normalized signal files, escalations (with packet), peek (DB + the role's `view.jsonl`), bounded command history and one-command status |
| `OperatorCommands` | `send(command) -> Ack`. Inserts the typed command row (a database that stays locked past its 5 s busy timeout raises `DatabaseError`, the CLI's readable exit, and queues nothing: retry); if the engine is up, waits up to 10 s for `done`/`rejected`; if it's down, returns `queued` ("applies when the engine starts"). The client message distinguishes engine-down queueing from an elapsed acknowledgement wait; both remain `pending` in storage until handled. Delivery is at least once and handlers are idempotent by command id (03 §7), so a command applied just before an engine restart is acknowledged `done`, never `rejected`, when replayed |
| `EventFeed` | `read(since, kinds, task)` and `wait(since, kinds, task, timeout)` over `events` |

`StateReader.command_history(limit, offset, status)` returns one bounded newest-first page and its continuation metadata; `command_status(command_id)` reads one row and `pending_command(command)` checks for a matching pending payload. Submit matching ignores only the task ID allocated by the store; all entered submission fields still participate. `OperatorQueries.command_history(expanded=False)` reads the three newest; expanded project history uses 20-row UI pages, each capped at 50, with an all-status or status-filtered continuation. Stored `pending`, `done` and `rejected` are shown as **Pending**, **Applied** and **Rejected**; **Sending** is local to a form. An elapsed acknowledgement wait is not a rejection. A recovered pending row shows current engine liveness and leaves its original acknowledgement wait context unknown because the command row does not persist it.

## 2. CLI

- **Global options**: `--project PATH` (default: nearest ancestor with `.shikiru/`), `--json`, `--set k=v`.
- **Exit codes**: `0` ok, `1` error, `2` usage, `3` not initialised, `4` command rejected.

The CLI gets an Operator into a project, in and out of its session, and back out again. It is not a second copy of the operator surface: **every mutating action except `submit` lives in the dashboard palette (§5.5) for humans and in MCP (§4) for AI Operators and scripts.** One action, one adapter.

| Command | Purpose |
|---|---|
| `init [--yes]` | Wizard (§3); `--yes` writes the detected defaults |
| `start [--attach]` | Validate config and plugins, start the engine, ensure the session. On a running engine it only ensures the session. A name collision with another project fails with a hint to set `project.name`. `start` waits up to 5 s for the new engine to hold its lock and fails at once when the engine process has already exited. The detached engine's stdout and stderr go to `.shikiru/logs/engine.out` (0600, truncated by each start, so it holds the current start's output only, normally empty); the error of an early exit or a lock timeout ends with its last 2000 bytes, so a crash before the engine log exists is never lost |
| `stop [--kill-session]` | Stop the engine; running turns are stopped (their sessions persist) and re-run by resume on the next start. The ack is returned once the engine has released its lock, so `stop && start` is safe; if the lock is still held after `orchestration.shutdown_seconds` plus `TURN_STOP_GRACE`, the command fails |
| `ls [--host H]` | Every Shikiru project on this host, or on `H` (§5.6): name, directory, engine state, running and queued counts, open escalations |
| `attach [NAME] [--host H]` | Attach to a session; with no `NAME` and more than one match, the picker (§5.6) |
| `submit "<request>" [flags]` | Prints the `T-n` id (05 §1 flags) |
| `status [T-n] [--watch]` | Without an id: one project, engine, slot, queue and escalation summary, then populated task, queue, escalation and fault sections, compact per-agent usage and observed quota windows, run-directory count and size, and the stopped engine-output path when present. Task rows retain title, state, step and acting role where known, holds, wait reason, slot and queue priority; fault rows retain scope, task, error class, first and last seen, repeat count and recoverability. Token input/output coverage remains explicit, billed amounts and API-equivalent estimates stay separate, and absent values remain unknown. With an id: only that task's identity and current state, holds and blocker/outcome, retained reports and verdicts, event timeline, branches and session role/agent/model/status/session ID/effort. Empty sections are omitted; there is no comic-strip frame or repeated project usage. An unknown id keeps the existing project-status fallback. `--watch` continues to refresh from `StateReader.on_change`; non-TTY output appends plain status updates without cursor controls |
| `doctor [--probe]` | A non-empty `engine.out` is listed as an `engine-output` check (informational), and `status` prints `last engine output: <path>` while the engine is down; environment (tmux ≥ 3.4 and git ≥ 2.45 fail the check below those versions), repository-root (D20), config and plugin checks; `--probe` validates the configured ladders (04 §3): live contract check 1 on each agent's first rung and a smoke turn on every other distinct rung, showing the stream tail and stderr when a probe fails |
| `mcp` | Stdio MCP server |
| hidden: `engine`, `dash`, `palette`, `view`, `report` | Process entrypoints. `view T-n ROLE` is the live view a role pane runs (§5.1) |

**Output**:
- Human command output uses the shared Focus ledger palette and renderables (§6) with open sections and unframed outcomes; it inherits the terminal's font and background.
- `ls` uses open session rows with the full session identity, project directory, engine state and running, queued and escalated counts. A supplied remote host appears once; narrow output wraps complete row facts under their session, and an empty result is explicit.
- `doctor` uses one open row per check with its outcome, name and full detail, then an aggregate result. Probe failures retain the stream tail and stderr; an `engine-output` check is informational and remains passing.
- `status` starts with the project and engine/slots/queue/escalation counts, oldest escalation age when present, and run-directory count and size. Only populated task, queue, escalation, fault, usage and quota sections follow. Fault timestamps, repeats and recoverability, separate input/output token counts and provenance, quota reset and observation times, and the stopped engine-output path remain readable in open rows. `status T-n` contains only that task's state, holds and outcome/blocker facts, retained reports and timeline, branches and full session identities; it does not repeat project task rows or aggregate usage. An unknown task ID retains the existing project-status fallback.
- Native Typer help keeps its existing layout, wording, ordering, defaults and wrapping; the shared semantic palette changes its styles only. Hidden process entrypoints stay hidden.
- Interactive `init` keeps the seven existing steps and choices. It uses the shared Focus theme, sentence-case step and field headings, ordinary fields, and compact Back/Next/Run doctor/Cancel controls. Its key hint styles Tab, Enter and Esc through `ui.keys`; validation and detection errors remain readable. Compact resize keeps a focused field visible in the scrollable form. Finish shows the absolute written config path and every real Doctor result with its full detail, including failing checks. The post-wizard success result shares the human init outcome but omits the placeholder-model warning because the wizard requires explicit models; `init --yes` keeps its absolute path and placeholder-model review warning. `start` says whether it started or reused the engine and names the ensured session. Successful `stop` says the engine stopped or was already stopped and whether the session was left unchanged or closed by the request. A pending acknowledgement keeps its command ID and reason without claiming an effect; a rejection keeps its command ID and cause.
- Domain errors preserve their cause and relevant context. When the project is not initialized, the CLI names the missing project state and directs the Operator to run `shikiru init` from the repository root.
- Known local paths use OSC 8 links only in terminals known to support them; the full literal path remains readable when links are unavailable.
- One-shot human CLI reports under `NO_COLOR`, `TERM=dumb` or non-TTY output are monochrome and linear without cursor control. The inline Textual wizard and attachment picker remain interactive keyboard/click interfaces with a scrollable form or session list; this one-shot output policy does not describe their screen layout. `NO_COLOR` keeps useful text and focus cues, and reduced-color terminals use Rich's automatic color support for CLI reports.
- `--json`, bare task IDs and versions, MCP stdio, pane streams and evidence exports keep their existing machine-readable output. Human renderables treat path, error, task and other stored values as literal text, not Rich markup.
- Long human operations may use Rich's existing progress facilities only on interactive human output, with completion and error cleanup; protocol stdout never contains progress.

## 3. `init` wizard

`dashboard/wizard.py` is an inline Textual app. It shares `operator/detectors.py` with `init --yes`. Its seven existing steps use the shared Focus theme and palette, sentence-case headings, ordinary fields, and shared button and key treatment. The form keeps Back/Next validation, drafts and choices; validation returns focus to the field with the error. Focused controls remain in the scrollable body after resize. At heights below nine rows the title folds away to preserve form space while the navigation hint remains visible. Escape cancels before configuration is written and returns the written result after it is written. Finish shows the absolute config path and every check from the real Doctor report, with full details and semantic pass/fail styling; a failing Doctor report remains visible before the command returns its error status. User and plugin values are rendered as literal text. The final Next transition leaves focus on Run doctor, so Enter runs it:
1. **Repository**: the project root must be a git repository root (`git rev-parse --show-toplevel` equals it); otherwise `init` fails naming the path (D20). `base` = the current branch.
2. **Agents**: installed plugins whose `doctor()` passes. Enter explicit `agent:model[:effort]` ladders for leader, implementer and helper; the empty model field requires an operator choice.
3. **Trackers**: scan Markdown files up to four path components from the repository root, skipping `.git` and `.shikiru`; select files under a `tasks` directory or whose stem starts or ends with `plan` or `todo` (case-insensitive).
4. **Caches**: existing git-ignored paths with common cache directory names, preserving repository-relative paths, plus a CoW support check.
5. **Parallelism**: set the maximum number of active tasks.
6. **Integration mode**: choose local merge or pull request integration.
7. **Finish**: write `.shikiru/config.toml`, add `.shikiru/` to `.git/info/exclude`, run `doctor`. `init --yes` writes the editable `default` model placeholder, so review the role ladders and run `doctor` before `start`.

## 5. Dashboard

### 5.1 tmux session

- **Name**: `[shikiru] <project.name>`, with `.` and `:` replaced by `_`, always targeted as `=[shikiru] name`. The session env stores `SHIKIRU_PROJECT_DIR`.
- **Size**: the session is created detached at 240×64, so views get readable panes before anyone attaches; an attaching client resizes it as usual.
- **Terminal title**: the Shikiru session enables tmux title updates and sets the terminal title to the project name, without a Shikiru prefix.
- **Options**, set at the scope tmux gives each one:
  - *Session*: `base-index 0`, `renumber-windows off`, `mouse on`, and the project terminal title. These session-local options keep Home at index 0 and stop a removed Home from shifting a task or operator window into that slot, even when the user's tmux server uses another global base index; the global settings are unchanged. If an unrelated window already occupies index 0, session recovery reports the collision and leaves it intact.
  - *Task window*: `remain-on-exit on`, `allow-rename off`, `automatic-rename off`, `allow-set-title off`, `pane-border-status top`, `pane-border-lines heavy`.
  - *Home window*: the same lifetime and rename options, with `pane-border-status off`. The top pane-border row is Shikiru's own extra Home chrome; the Home identity row remains and task role labels keep their border row. Project-session status styling is local to that session; server-wide defaults and unrelated sessions remain unchanged (§5.3).
  - A window option set at session scope reaches only the session's current window, so `remain-on-exit` in particular must be set per window: without it a dead pane disappears instead of staying for the guard (§5.2).
- **Windows**:
  - The permanent home window is `dashboard` (`0:dashboard`), running `shikiru dash --home`. Start and session recovery identify it by its owned pane marker or command, so renaming it does not create a second Home. A restart restores its name and index. When two identified Home windows exist, recovery retains the preferred active Home and removes the duplicate without moving unrelated window identities.
  - Each active task has its own window, named exactly by `titles.window`, built from `dashboard.layout`. It is created at dispatch and closed at a terminal status. New task windows and their splits are detached: dispatch and guard restoration leave the attached client's current window and pane unchanged. Explicit task or role navigation and takeover still select the requested target.
- **Role panes** run `shikiru view T-n ROLE`: a read-only Rich live tail of `runs/T/<role>/view.jsonl` (turn boundaries with step and rung, messages, tool calls, usage, failures) through `ui.StreamLine`. Tool completion lines include recorded success/failure and an available exit code; missing facts and older rows remain unknown. The view does not add raw command, output, prompt or path content. It writes nothing and survives engine restarts. While the role is taken over (03 §9), the pane runs the agent's own TUI instead.

### 5.2 Layout and protection (`LayoutGuard`)

- **Build**: the packaged layout is a full-width vertical stack: Leader 40%, Implementer 40%, and a Project folder shell at 20%. It omits the system pane. The tree is built with detached `split-window -h|-v -l <size>%`; `{role: pane_id}` is stored in `tasks.panes`. Projects with no layout override inherit this default. Existing explicit overrides, including special panes such as `system`, remain unchanged until the operator edits or removes the override.
- **Guard**: every `poll_seconds`, the engine first recreates the session and its home window if the tmux server or session is gone (02 §1), then the guard compares each task window with the DB.
  - A missing configured pane (killed) is recreated beside surviving leaves in the layout. Restoring a missing pane preserves surviving pane ids and processes, then reapplies a direct vertical stack's configured geometry.
  - A dead configured special pane or view pane is respawned.
  - A dead taken-over pane (the Operator exited the TUI) becomes a `HandBack`, which respawns it as the view (03 §9). A taken-over role whose pane is gone (tmux server loss, host reboot, a killed pane) is rebuilt, never as a read-only view of a held role: `LayoutGuard` appends `takeover_lost` and queues the `HandBack` (03 §9). Neither path restores the take over: the role's pane shows the view, and only a new take over makes it interactive again.
  - Each restoration emits `pane_restored`.
  - Whenever role panes are created or rebuilt (a new window, a restarted session, a killed pane), their titles are re-applied from stored task and run state, so a recreated pane never shows the tmux default (§5.3).

  There are no global key-binding overrides, so closing a pane has no lasting effect.
- **Palette key**: one conditional binding uses the effective inherited or session-specific prefix. In a live Home pane, `prefix + Space` sends F12 to the current pane so its mounted `DashboardApp` opens contextual Actions over Home. In other `[shikiru]` panes it opens the standalone `shikiru palette` app in a tmux popup (the same Actions list without dashboard routes or Extensions) and passes the originating `#{pane_id}` through hidden `--origin-pane`; task and role come from the project's recorded pane mapping rather than popup-inherited `TMUX_PANE`. Unrelated sessions keep tmux's `next-layout` default.

### 5.3 Titles and decorations

- **Titles** use the `dashboard.titles` templates. Task window names use `dashboard.titles.window` unchanged, without a Shikiru or project prefix. The packaged shell title is `Project folder · {cwd}`; an explicit title override is preserved. Fields:
  - `task_id`, `title`, `project`, `role`, `role_label`, `glyph`, `agent`, `model`, `effort`: effective settings of the recorded role session when one exists, otherwise the selected rung
  - `pending_rung`: an optional `· next agent:model/effort` suffix when the configured rung differs from the effective session
  - `iteration`, `step`, `status`
  - `context`, `cost`: preformatted (`42%`, `$1.84`), `–` when the agent reports no value (04 §1)
  - `context` colour: classified on the whole percentage the title shows (39.6 shows `40%`, so it is amber): sage below `dashboard.titles.context_warn_pct` (40), amber from there below `context_alert_pct` (60), dusty rose at 60 and above, using the §6.1 palette. Unreported context stays secondary grey with `–`. These pane-title thresholds are separate from the subscription-limit gauges (`dashboard.gauges`: 50/90, §6.1).
  - `flags`: glyph-prefixed hold and state words for existing templates; `flags_text`: the same readable words without glyphs, including `operator` while a role is taken over
  - `active`, `queued`, `max_parallel`, `cwd`
- When the configured rung names another agent, Take over remains on the agent that owns the current session. The pending title suffix shows the selected agent; that agent starts in a fresh session at the next automated turn, with the report hand-off described in 03 §4.1.
- Role pane titles are re-applied from stored state whenever `LayoutGuard` creates or rebuilds panes, without waiting for a usage report or a task transition; no title state is persisted.
- Packaged Leader and Implementer titles use the role word and `flags_text` without role or state glyph prefixes. The `glyph` and `flags` fields retain their existing values, so an explicit custom template that uses them keeps its chosen glyphs; Shikiru does not rewrite project configuration.
- A role that is handed back, or rebuilt after its pane was lost, is titled as a view again: the `operator` flag, the `glyph` field and the `@shk_color`/`@shk_glyph` pane state return to the role's own values (or the `pause` state, while paused). The task's `intervention` hold, while another role is still taken over, keeps the `operator` flag in its role titles (03 §9).
- **Decorations** follow §6.1:
  - Project-session status uses the graphite background for the full row, including its blank fill and left/right segments. Its clock is local wall time and date with seconds; tmux refreshes the native status at one-second intervals.
  - Home and task windows show their actual index before their existing name, including `0:dashboard`; current and inactive styles and formats are set on each project window. Task panes keep their unchanged title text in `pane_title`; border-row components use role, agent/model, effort/iteration, context/cost and recorded ownership/state fields with the §6.1 palette. Pane-border styling and its recovery apply to owned Home/task windows only, including the full title row and blank fill. Existing task windows are recognized through their recorded Shikiru state metadata; recovery does not infer ownership from a window name. Operator-created windows retain their pane-border, lifetime and rename settings. Global tmux styles and unrelated sessions remain unchanged.
  - Window options `@shk_state_color` and `@shk_state_glyph` feed the window-status formats; pane options `@shk_color` and `@shk_glyph` remain available to explicit custom formats.
  - `TurnMonitor` and `TaskFlow` update title and state fields when their source facts change; tmux refreshes the wall clock natively.

Phase 11 Tasks 105–112 delivered the first current selection, overlay, layout and native verification routes; Tasks 113, 113a and 114–128 completed accepted second- and third-review work. Task 128's connected walkthroughs and native verification are in the third-review record. Phase 8's operator service behavior remains in force: state changes still go through `OperatorCommands`, browser/detail queries remain bounded, the engine stays the single writer, and existing widgets and callbacks remain compatible. See the [first-delivery record](../release-readiness-2026-10-07-phase11.md), the [second-review record](../release-readiness-2026-10-08-phase11-followup.md), the [third-review record](../release-readiness-2026-10-09-phase11-third-review.md) and historical [Phase 9 record](../release-readiness-2026-10-04-phase9.md).

`shikiru dash --home` is the mounted Textual Home workspace. The packaged task window contains the Leader view, Implementer view and Project folder shell from `dashboard.layout`; it has no dashboard or system pane. The standalone `shikiru dash --task T-n` entry remains available for an explicit task-focused dashboard. An explicitly configured `system` layout leaf is restored as a shell; to use it for a task dashboard, the operator must replace the pane command with an explicit current-project `dash --task T-n` invocation. `LayoutGuard` does not start that view automatically.

Home uses configured widget placements to build compact identity/engine and uptime, operating-count, project-usage, Host/Shikiru/Agents resource and attention-strip readouts. In the shipped configuration the strip stays visible: a quiet project says `✓ No decisions needed`, and an actionable decision or fault appears in that same strip when needed. It splits list and inspector at 73 columns or wider and stacks the inspector below that width; at 20×8, identity and task detail remain reachable by scrolling. The footer hides below 9 rows; selection clear, contextual Actions and Help remain available through Escape, `Ctrl+P` and `?`, while tmux prefix+`d` detaches the client. The latest durable command follows the footer actions at wide widths and wraps or truncates with the compact footer; its focusable summary opens full history by mouse or Enter. With the footer hidden, command history is not offered on Home. The compact palette keeps its focused control reachable by scrolling; short text areas retain an editable row.

Tab and Shift+Tab visit only controls an operator can see and act on: the task list (in Home the active and `Recent` lists are one selection list, so only the one holding the selection is a stop), the task detail when it has content to scroll, its inline buttons, the footer buttons and status line, Usage, Resources, and the attention strip while it holds a decision, stall or fault. Layout containers (the readout and root scrollers, the attention scroller, the footer grid) and a quiet attention strip are skipped; a click on a summary still focuses the strip, and mouse wheel and Page keys still scroll the readouts through a focused readout. Focusing a readout fills every wrapped content row with the selected surface (never the rule above Resources) and never scrolls the page, selects a task or writes a command. Startup focus stays on the task list; while at least one decision exists the strip renders it in that same armed surface regardless of focus, so its `Enter …` hint is meaningful. The strip follows the selected task: a task with a decision shows its first (or the one chosen with Left/Right), a task without one reads `T-12 · No decision needed` (`T-12` bold white, the status white) with the `Ctrl+P actions` hint and, when decisions exist elsewhere, a grey `· N decisions on other tasks` (`1 decision on other tasks` for one); with no selection (or after Escape) it shows the first pending decision. Diagnosed stalls, engine faults and engine status keep precedence, following the selection never moves focus or writes a command, and the bar names a decision's reason in words (`Decision required`, `Integration blocked`) from the persisted reason while `E-n` and `T-n` render bold. Up and Down select tasks from the strip, usage, resources and the footer, never scrolling the page instead; the strip never cycles its groups with them and, only with no attention groups, scrolls the compact status when it overflows, the only keyboard route to its hidden lines at small sizes. The task list, text inputs and text areas, expanded Selects, arrow lists and modals other than the task detail keep their own Up and Down. Left and Right choose among the followed task's decisions only when it has two or more and otherwise do nothing; Enter, `o` and `r` act on the displayed decision.

Home preserves the existing `dashboard.widgets` list and shipped default. `header`, `queue`, `escalations`, `usage` and `resources` fill their Focus readout/list placements only when configured. Running, Waiting and grouped Attention are shown as a short operating-count line; the configured attention strip is always present and shows either the quiet state or a concise actionable item. They are not separate cards or permanent navigation controls. Running counts `running` and `integrating` tasks with no holds, scheduler wait reason or recorded current-turn quota wait. Waiting counts non-terminal queued, escalated, held, scheduler-waiting or recorded current-turn quota-wait tasks. Attention counts grouped task/project rows, so multiple reasons for one task remain one row. These categories can overlap and are never presented as an additive project total. Occupied slots continue to use `occupied_slot_ids`, including paused tasks and pull-request waits; slot occupancy is not the Running count.

Usage names its scope as project recorded runs or the selected task's runs; the project popup is titled `Project usage`. Its body has three sections, each fact appearing once. **Totals** are labelled rows: `Totals` (`62 sessions · 62.5M tokens · $4.28 API`, the Home-bar groups, plus a bold green `$X billed` only for non-zero billed spend in any mode that differs from the API amount, never a bare `$0.00 billed`), `Tokens` (`in · out · cache r · w`: grey labels, bold cyan numbers; cache omitted when both counters are zero), `Coverage` (reported, legacy and without-token session counts, shown only when some session lacks reported tokens) and `Billing` (subscription, API billed, API unreported and unknown-mode session counts, then the amber `est. $… API-equivalent (n sessions)` estimate on its own row). **By agent** has one row per agent that has runs (`claude 30 runs · 40.0M tokens · $4.28 billed`; an estimate reads `est. $…` in amber; partial token or cost coverage follows as a grey qualifier such as `2 without tokens` or `1 cost unknown`). **Limits** has one gauge row per reported quota window (`5h ◑ 38% resets 1h 40m`), with a single `observed 2m ago` line when every window shares one age and a per-window `· observed …` suffix otherwise; the section is absent when no window is reported. Counts and totals are bold white, bold cyan or bold green, labels and qualifiers grey, estimates amber; sessions are called `sessions` in Totals and `runs` per agent. Rows wrap only at ` · ` boundaries with a hanging label column, and below 32 columns each label stacks above its values so nothing is truncated. Raw billing sources (`operator_config`, `provider_reported`) never appear in the panel. A project with no runs reads `0 sessions · tokens unknown` and `No runs or quota windows recorded.`. Billing declarations: set `[agents.<name>.options].billing_mode` to `api`, `subscription` or `unknown` for new sessions; existing sessions keep the mode and source recorded when they started, and an unknown mode is either explicitly configured, provider-reported or unavailable (historic cause unknown). Token totals include explicit `UsageReported` sessions and legacy runs with positive token evidence; all-zero legacy token columns stay unknown, with explicit, legacy and unknown coverage shown. A quota-only agent has unknown token values. Billed and API-equivalent subtotals remain separate; a `cost unknown` count keeps partial subtotals from reading as complete spend, and token provenance beyond reported, legacy and without-token counts is not displayed. Zero is shown only for a recorded zero. Quota gauges use only reported windows and display the reported reset countdown and `observed_at` age; they are sage below `dashboard.gauges.quota_warn_pct` (50), amber from there below `quota_alert_pct` (90) and dusty rose from 90 upward, on the displayed whole percentage (§6.1), and a stale observation keeps the colour of its value. The project usage and selected-task run aggregates are cached by SQLite `data_version`; motion refreshes only advance countdowns and observation ages.

The Resources widget samples at its configured cadence outside motion callbacks; the Project diagnostics popup re-reads the same cached observations and never starts a second sample. The resource groups are Host CPU/used RAM, Shikiru CPU/RSS excluding agents, and this project's Agents CPU/RSS. CPU shows one decimal below 10% (`0.3%`) and an integer from 10% up. Host RAM is used/total against the sampled host total; Shikiru and Agents show process RSS labelled `RSS` with no denominator, not host-used RAM or a per-process limit. It distinguishes an empty process tree from a measured zero, an absent Docker CLI/daemon as unavailable, and failed samples as failed. A sample is stale only after a later sampling failure kept the last complete timestamped observation, which then shows the sampling error; a sample that is merely old stays available. A section shows an age only in that state (`stale · observed 2m ago`, amber, taken from the stored sample timestamp); fresh, empty, failed and unavailable states and the whole Resources section show none. `faults` lists each open engine-fault streak as `task · scope · error · recoverable` or `unrecoverable` with `×repeats`, then its `first` and `latest` timestamps, and renders nothing while no fault is open. A failed diagnostic source leaves the other panels and task browser available.

### 5.6 `ls` and `attach`

`SessionLister` returns one row per project, for the local host or for `H`; `ls` prints the rows, `attach` picks one from them. Human `ls` output keeps each complete session identity, directory, engine state and running, queued and escalated counts together in an open row. A remote host is shown once above its rows. Long facts wrap without truncation, and an empty listing is stated explicitly; JSON continues to contain only the existing row schema.

- **Rows**: `tmux list-sessions` filtered by the `[shikiru] ` prefix and each session's `SHIKIRU_PROJECT_DIR`; engine liveness comes from the project's `engine.lock`, while running, queued and escalated counts come from its DB. `ls` opens each DB with SQLite read-only mode and never changes its schema, progress or other project state. SQLite may create or update WAL and shared-memory coordination sidecars while reading a WAL database; a newly created WAL file is empty, and existing database or WAL contents remain unchanged.
- **`attach`**: exactly one row, or a matching `NAME` → `os.execvp("tmux", ["tmux", "attach", "-t", "=[shikiru] NAME"])` (`switch-client` when inside tmux). Otherwise an inline, scrollable list of the same complete session facts as `ls`. Up/Down and Enter or a click select the exact row; Esc cancels. Long paths wrap, the selected session remains visible after a compact resize, and list scrolling makes all row facts reachable. Selection uses only the shared `selected-surface` background, with a bold row as its monochrome cue and no selection glyph.
- **Remote** (`--host H`, on both): `ssh H shikiru ls --json` gives the rows; `attach` then runs `os.execvp("ssh", ["ssh", "-t", H, shlex.join(["tmux", "attach", "-t", "=[shikiru] NAME"])])`. `--host` needs nothing installed locally but `ssh`, and nothing remote but `shikiru`.

### 5.7 Notifications

Home attention is a read-only projection of durable decisions, current diagnosed task stalls and recorded open fault streaks. It does not acknowledge decisions or deliver notifications. The engine lock remains the liveness source; fault events and role signals provide separate evidence. Informational retries, quota waits, expected rework and deliberate pauses keep their workflow meaning.

`Notifier`, on `escalation`, `task_done`, `integration_waiting` (a local merge waits for a dirty checkout, 03 §6), `takeover_lost` (a taken-over role was handed back because its pane was lost, 03 §9), `engine_fault` (the first fault of a failing tick streak, 02 §1) and an `engine_stopped` that carries a `reason` (the engine stopped on a fault rather than on request):
- runs `tmux display-message` in the session;
- runs `notify.command`, when set, with the event JSON on stdin (for Slack, ntfy or a remote AI Operator). A non-zero exit, a timeout (`notify.timeout_seconds`, 30 s by default) or a missing command is logged with the event id and recorded as an `engine_fault` of scope `notification hook`, once per streak (02 §1).

Delivery never runs on the command loop. The `Engine` queues each notifiable event on `NotificationDelivery`, which delivers urgent events on one task and informational events on another, each lane one at a time, so a hung hook cannot delay `stop`, `pause` or scheduling. Events have two priorities: *urgent* (`escalation`, `engine_fault`, an `engine_stopped` with a reason) and *informational* (`task_done`, `integration_waiting`, `takeover_lost`):
- urgent events have their own delivery slot: they are delivered in order and never dropped, and a stuck informational hook (killed after `notify.timeout_seconds`) never delays one; only an earlier urgent hook still in flight can, and that one is killed after the same bound, so a stuck hook delays but cannot silence an escalation or a fault. The hook may therefore run twice at once, once per lane;
- the informational backlog holds 64 events; when full, the oldest informational event is dropped with a logged warning;
- a delivery failure is logged and the next event is delivered;
- the engine loop supervises both tasks like the task flows: an unexpected failure is logged and the task restarted;
- a hook runs in its own process group, which is SIGKILLed on its timeout and on cancellation, so no descendant it started outlives the hook (03 §4.2);
- the delivery cursor is durable (`notification_cursor`, 05 §2): it holds the id up to which every urgent event has been delivered, trailing the oldest urgent event still queued or in flight, and the engine writes it on each poll and at stop. A restarted engine replays the urgent events after the cursor, in order and ahead of any new one, so an escalation or fault committed shortly before a crash or kill, or still queued behind a stuck hook, is notified after the restart. Informational events are never replayed, and the first start of a project begins at its latest event. Delivery is at least once: an event delivered after the last cursor write (at most one poll, 0.25 s) before a kill is delivered again, as is a fault stop notified directly at stop, and a hook that failed or timed out counts as delivered (it is recorded as a `notification hook` fault, not retried);
- on engine stop the tasks are cancelled, which terminates a running hook, and pending events are not delivered by this engine (urgent ones are replayed by the next), so `stop` never waits for a hook. The one exception is the `engine_stopped` event of a fault stop: it is delivered directly, bounded by `orchestration.faults.stop_notify_seconds`.

### 5.8 Keeping the engine running

`shikiru start` spawns the engine detached; nothing restarts it if the process dies (a fault stop, an OOM kill, a reboot). To keep it running, run the hidden entrypoint under a service manager and restart it on failure. A restarted engine reconciles persisted state (03 §7) and recreates the tmux session (02 §1). Give the service the `PATH` your agent CLIs, `git`, `gh` and `tmux` need. `shikiru start` reuses a running engine, so it remains the way to ensure the session and attach.

The engine stops gracefully on SIGTERM and SIGINT (03 §7), which is how `systemctl stop` and `launchctl bootout` end it, and exits 0; a stop that outlives `orchestration.shutdown_seconds` (15 s) or a second signal ends the engine and its turn processes by force and exits non-zero. Keep the manager's stop timeout above the bound plus the 10 s turn kill grace: systemd's default `TimeoutStopSec` (90 s) already is, launchd's default `ExitTimeOut` (20 s) is not, hence the explicit values below.

The unit files below show the shape; they are documented recipes that CI does not run.

systemd user unit, `~/.config/systemd/user/shikiru-myproject.service`:

```ini
[Unit]
Description=Shikiru engine (myproject)

[Service]
ExecStart=/path/to/python -m shikiru --project /path/to/myproject engine
Environment=PATH=/usr/local/bin:/usr/bin:/bin
Restart=on-failure
RestartSec=10
TimeoutStopSec=30

[Install]
WantedBy=default.target
```

launchd agent, `~/Library/LaunchAgents/dev.shikiru.myproject.plist`:

```xml
<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE plist PUBLIC "-//Apple//DTD PLIST 1.0//EN" "http://www.apple.com/DTDs/PropertyList-1.0.dtd">
<plist version="1.0"><dict>
  <key>Label</key><string>dev.shikiru.myproject</string>
  <key>ProgramArguments</key><array>
    <string>/path/to/python</string><string>-m</string><string>shikiru</string>
    <string>--project</string><string>/path/to/myproject</string><string>engine</string>
  </array>
  <key>EnvironmentVariables</key><dict><key>PATH</key><string>/usr/local/bin:/usr/bin:/bin</string></dict>
  <key>KeepAlive</key><dict><key>SuccessfulExit</key><false/></dict>
  <key>ThrottleInterval</key><integer>10</integer>
  <key>ExitTimeOut</key><integer>30</integer>
</dict></plist>
```

`Restart=on-failure` and `SuccessfulExit=false` restart the engine after a fault stop (non-zero exit) but not after `shikiru stop`, `systemctl stop` or `launchctl bootout` (exit 0).

## 6. Visual design: comic strips with a semantic visual language

The comic strip and palette below describe Phase 8's shipped visual presentation and remain available for CLI and explicitly opened workflow detail. Tasks 93–94 apply the graphite/steel/sage/amber/dusty-rose Focus palette to Home and task detail. The shared task detail follows [Compact Operator TUI](../tui-focus.md#2-composition-and-palette), which supersedes the expanded strip composition and role colors with compact state/activity and combined usage. The meaning of task state, role, hold, ownership and signal-driven activity remains; compact views keep text and glyph alternatives, motion limits and monochrome access.

Shikiru's look comes from **structure and meaning**:
- tasks are 4-panel comic strips (*yonkoma*);
- key moments are speech bubbles;
- escalations are splash panels.

Every colour, glyph and movement answers one of three questions: *who acts*, *what state*, *how alive*. English carries all meaning; kanji are decorative marks. Everything lives in `ui` and is shared by CLI and dashboard.

### 6.1 Tokens and glyphs

**Colours**: the Textual shell, palette, task detail and evidence forms share one named palette. Focus and activity use steel blue; successful reported charges use sage; holds and decisions use amber; errors use dusty rose. Role and state words carry meaning without role-specific neon colors. Truecolor has 256/16 terminal fallbacks; `NO_COLOR` retains readable words and the existing bold, dim and reverse cues. Selection (fold headers, list rows, the Tasks list and the session picker) is the `selected-surface` background alone, with no glyph; a selected fold header or `RowList` row also keeps its bold name. The `detail-surface` background (`#1c2530`, between the page and the selection) shades read-only detail blocks such as the full text under the Events and Agent activity lists.

**Diagnostics sections** (Tasks 151–154): every section of the Project diagnostics popup and the standalone Docker, Disk and Faults views draws the Usage panel's neutral-border rule and grey heading, grey labels, bold primary-text row names and bold steel-blue figures. `NO_COLOR` keeps those bold weights and maps each colour to its Textual luminance grey. The Disk free level shows a ` ‼` marker at warn and alert, so it stays readable under `NO_COLOR`.

**Title casing** (Task 164): every displayed title, heading, menu entry, button, hint and action name uses sentence case: the first word is capitalised and the rest lower case except proper nouns and identifiers (Shikiru, Docker, Esc, Ctrl, task IDs, key names). Segments after ` · ` and labels after a key are lower case (`Diagnostics · docker`, `u details`, `Ctrl+P actions`). The masthead `SHIKIRU` (bold steel blue, bold kept under `NO_COLOR`) is the only upper-case exception; the surface heading reads `Tasks`. The rule covers titles, headings, menu entries, hints and action names, not status sentences (`T-12 · No decision needed`, `observed`), which keep their specified wording. Stored values, command kinds and file formats are unchanged.

| Token | Colour | Meaning |
|---|---|---|
| `background` | `#11151b` | Application background |
| `surface` | `#171d25` | Ordinary panel surface |
| `neutral-border` | `#3d4654` | Section edges and separators; popup frames use steel blue |
| `primary-text` | `#dce2e9` | Main text |
| `secondary-text` | `#9aa5b5` | Supporting text |
| `focus` / `steel-blue` | `#83bddd` | Keyboard focus and observed activity |

| `alert` / `dusty-rose` | `#e3a0a0` | Errors and diagnosed stalls |

Quota gauges, the only gauges, use sage below 50%, amber from 50% below 90%, and dusty rose from 90% upward (`dashboard.gauges`), on the displayed whole percentage; CPU and RAM are text with no thresholds, and agent pane-title context uses the §5.3 thresholds (40/60). All roles share the quiet steel accent where color helps; text and glyphs identify each role.

**Glyphs**: one set, registered in `ui.glyphs`. A unit test rejects wide and emoji-presentation characters. Ambiguous-width characters are allowed and drawn one cell wide, as Textual assumes; terminals set to CJK ambiguous-wide are unsupported. Glyphs that have an emoji variant carry U+FE0E (`⚖︎ ⚙︎ ⏸︎ ⚠︎`).

The compact task readout uses English stage and state words and the registered one-cell activity glyph. Kanji remain decorative only in the retained `TaskStrip` renderable, which stays available for CLI output and configured strip plugins; compact task content does not require kanji or color to explain workflow state.

- **Panels by mode**:
  - implement: Triage · Implement · Verify · Merge (or PR)
  - plan: Triage · Plan · — · Merge
- **Panel state**:
  - pending: dim, dotted border
  - active: heavy border in the acting role's colour, spinner, role glyph, iteration
  - done: green `✔` and duration
  - rework: orange `↺n`
  - escalated or failed: red `‼`
- During dispatch setup, a `running` task without a persisted step has one engine-coloured setup panel. If setup retries exhaust before the first step, its step-less escalation has the red escalation panel.
- **Stamps** drawn over the active panel, in the hold colour: `PAUSED`, `OPERATOR`, `QUOTA · resets 14:10`, `STALLED`.
- **Widths**: ≥ 60 columns gives the full strip; narrower gives one line, `T-12 ⚖︎ Verify 2/5 ◆ opus ⠹`.

### 6.3 Speech bubbles (`ui.SpeechBubble`)

`◆ Leader: “AC3 lacks a tier-2 test.”   T-12 · 2m` is one line in the speaker's colour.

**Sources**:
- verdict summaries (Leader);
- report summaries and questions (Implementer);
- `helper_action` events (Helper);
- `rung_changed`, `quota_blocked`, `scope_change`, `task_done` events (engine).

### 6.4 Splash panel (`ui.SplashPanel`)

`SplashPanel` renders the recorded escalation headline, question and options inside the configured attention view. Home presents a concise quiet message in the attention strip when no decision needs action and shows an actionable decision in that same strip when one does, naming its persisted reason as a readable label; its action and task context open the resolution screen (§5.5). The packaged task window has no system pane, and decisions do not create a separate pane or duplicate Home view.

### 6.5 Motion (`dashboard.animations = true`)

Motion is driven by real signals, so the dashboard shows how alive the system is:

| Motion | Meaning |
|---|---|
| Active panel spinner cycles while a task is in progress: a recorded live, unheld current turn (once a signal is recorded; quiet tools do not freeze it), or the engine's own work in the `integrate` step and the setup `Starting` phase, where no agent turn or signal exists. It stops when the engine is down, a hold, wait reason (PR/CI/retry), open decision, recorded integration wait or diagnosed stall applies. The signal age remains tied to the last recorded signal; engine-only work never claims one. Home task status blinks under the same predicate | Working vs waiting vs stalled vs stopped |
| Stamp flash (400 ms reverse video) when a verdict or merge lands | A turn outcome just happened |
| Escalation border pulses red/dim at 1 Hz while open | Needs attention |
| Elapsed time, quota countdowns and cost tick live | Live time and spend |

Motion comes from a pure `frame(state, now)` function with an injected clock, capped at 4 Hz. Setting `animations = false` renders static frames while the configured `refresh_hz` timer still updates state, ages and countdowns. Slow callback work does not delay other callbacks, and an in-flight callback is not started again until it completes; removing its subscription cancels outstanding work. Report, facts and packet evidence load on detail mount or relevant state/file change, not on each motion tick. `NO_COLOR` and `TERM=dumb` use readable textual state and focus cues so color and animation never carry meaning alone.
