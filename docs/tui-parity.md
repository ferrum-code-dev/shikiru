# Focus terminal parity correction

Status: Task 97 audit and target specification are complete; Tasks 98–102 are planned and no parity correction has shipped. Task 97 is recorded in [the implementation plan](../tasks/plan.md#phase-10-focus-terminal-parity-correction).

This specification is the normative visual and interaction target for Phase 10. It follows the approved [Focus Steel HTML reference](design/references/focus-steel-approved.html) and [736-pixel view](design/references/focus-steel-approved-736.png) one-to-one. Where the Phase 9 presentation prose in [Compact Operator TUI](tui-focus.md) describes a broader or looser layout or route, this specification takes precedence for composition and interaction. Phase 9 billing, evidence, plugin, engine, ownership, command and compatibility guarantees remain in force.

With the reference font and frame padding, these correspond approximately to 68–72 and 48 native columns. Confirm the mapping in Task 101; do not carry Phase 9's 100-column or height-only switch into the target. Compact comparisons use 48×20 and 36×14/20, with 20×8 retained as the minimum reachability floor.

## 3. Terminal composition and cell mapping

The terminal has a one-cell graphite frame and compact monospace content. At the wide reference grid, map visible rows in this order:

| Order | Terminal content | Cell and layout rule |
|---:|---|---|
| 1 | Brand, project name/branch, engine state and verified uptime | One line; identity left, engine and uptime right. Uptime is unknown unless the current lock holder matches recorded start evidence. |
| 2 | Slots, running tasks, waiting tasks and integration/repository condition | One concise line from current operator projections. Keep labels once. |
| 3 | Project input+output tokens and coverage, reported API charges and missing-cost count, declared subscription-agent count | One compact line when it fits. Unknown totals stay unknown. API-equivalent estimates never appear as spend. Use “subscription agents,” never guessed accounts or plans. |
| 4 | Host CPU and RAM used/total; Shikiru including agents CPU and RAM | Two aligned groups on one line at wide width. Reuse one timestamped resource sample. Preserve explicit failed, stale, unavailable and empty states when a value cannot be trusted. |
| 5 | One actionable attention item, only when a decision, fault or engine stop needs attention | One row, task/project target and direct action. No permanent attention panel and no duplicate count row. |
| 6 | `TASKS` with “Decision first” or an actual active count; active task rows; `Recent` completed rows | The list takes about 42% of available width. Rows are normal weight, unframed, with ID/title and concise state. Preserve current ordering rules within attention groups, stable selection and bounded history. |
| 7 | Selected task inspector | About 58% of available width, separated by one quiet vertical rule. Use the selected task's same identity and active/decision/hold state. |
| 8 | Keyboard hints and latest command feedback when relevant | One quiet footer row when height allows. Hint text may be mouse-active without becoming a permanent button row. |

The inspector order is fixed: task ID/title; state glyph and words; workflow milestone line; acting role, actual stage and elapsed value; situation; latest retained signal and recorded age; task token/charge summary with `u Details`; one role row per relevant session lineage; `e Evidence`. Rows can wrap to terminal cells. Avoid extra headings and blank panels between these items. Identity, decision, ownership and every hold remain visible or immediately reachable by scrolling at compact heights.

Use the existing Focus colors: background `#11151b`, surface `#171d25`, quiet border `#3d4654`, primary text `#dce2e9`, secondary text `#9aa5b5`, steel blue `#83bddd`, sage `#90cba6`, amber `#dfb16c`, and dusty rose `#e3a0a0`. The selected row surface is `#233340`, with a quiet steel outline. Use normal/light text weights for body rows and headings; brand and section labels may use restrained medium weight. No large bold header, bordered list bank, bright full-row fill, palette legend, role-neon colors or kanji decoration. Selection is shown by its surface and outline. Use width-safe textual state markers: `!` decision, the existing capped signal glyph for a live turn, `›` current workflow milestone, `✓` completed, `=` paused, `@` operator-owned role, `○` stopped and `·` queued or a later milestone. State words remain present in monochrome and disabled-motion modes.

All displayed amounts, counts, models, costs, reset windows, resource values, stage outcomes and elapsed ages come from retained project evidence or a current observed sample. The HTML's demo values are layout examples only. Do not add default accounts, model names, token/cost values, progress, elapsed durations or observed signals. Unknown, absent, stale, failed and incomplete evidence keeps its existing explicit meaning.

## 4. Existing facts and necessary additive projections

Reuse the current single-writer engine, `StateReader`, bounded task queries, usage aggregation, resource sampler, task evidence and plugin contracts. Do not create a second sampler, state reader, event stream consumer, session database, preference store or engine path.

Two compact values need compatible projections from existing observations:

- The resource snapshot currently exposes host RAM percent and available/free RAM. Add observed host RAM used and total from the same single `psutil.virtual_memory()` result already taken by `ResourceSampler`; carry them through the existing cached snapshot and resource view. Do not calculate used/total from percentage/available, or take another sample. Keep current sample cadence, timestamp/error/stale behavior, process-tree deduplication and scheduler threshold inputs unchanged.
- The task detail currently has bounded signal lines and a current-turn `signal_observed` boolean, but the compact signal lines carry no timestamp. Reuse the existing retained event/signal/timeline read to expose the latest signal and its recorded timestamp/age. If identity or time is missing, say so; never manufacture “just now.” Keep history bounded and show gaps when evidence was truncated or unreadable.

Stage milestones use existing task transition, report and progress evidence. Do not write new workflow milestones solely for presentation. A stage may be shown complete only when recorded evidence supports it; a bypassed stage remains bypassed, and a history gap stays unknown. Role/session rows use `acting_role`, ownership/holds and session history. `Current` means the role is actually acting or owned in the current task state; other observed role sessions are `Used`. `current_lineage` remains a separate session-history fact and is not a substitute for acting-role state. Session totals remain cumulative and may span models; do not attribute them to one model.

The `Recent` list uses the existing task browser/history queries and retains the same task identity and selection rules. Home readouts use current `HeaderView`, `RecordedUsageView`, `ResourceView`, `AttentionView`, `QueueRow` and `TaskDetailView` data. Configured widgets keep their entry points, callbacks and relative order in Extensions; secondary built-ins remain reachable on demand. CLI output, tmux role panes and engine/operator command contracts keep their existing semantics.

## 5. Keyboard, mouse and contextual routes

| Input or target | Required behavior | Command effect |
|---|---|---|
| Click a task row | Select that task and update the inspector. Preserve list/search/reading position. | None. |
| Up / Down | Select the previous/next task cyclically in the current task list. | None. |
| Enter on the selected task | Open the task inspector in the wide contextual overlay. In compact Home, open the shared full task detail; Escape returns to the same list selection. | None. |
| Ctrl+P | Open the selected task's contextual action menu; at Home with no task target, show applicable project actions. | None until a form is submitted. |
| `e` | Open selected task Evidence. | None. |
| `u` | Open selected task Usage Details. | None. |
| `?` | Open Help. | None. |
| Escape | Close the current menu/form/overlay or return to its caller, preserving task, role, selection, entered text and reading position. | None. |
| `/` in Home | Reveal and focus task search. Enter moves to results; Escape clears a nonempty query before hiding the empty input. Search remains hidden at rest. | None. |
| Click actionable attention row | Select the affected task and open its answer/resolution form directly. A fault or engine-stop row opens the corresponding evidence/action route. | None until submitted. |
| Click project token, billing or subscription summary | Open Project Totals and recorded subscription/quota details. | None. |
| Click Host/Shikiru resource summary | Open Diagnostics with the same cached observation. | None. |
| Click `u Details` or `e Evidence` | Open the corresponding task view. | None. |
| Click contextual action or form control | Select/open that action or submit only when the explicit submit control/key is activated. Inputs retain native editing keys. | Only explicit submission queues the typed operation. |

The Home footer presents `↑↓ select`, `Enter inspect`, `Ctrl+P actions` and `? help`; mouse users reach the same routes through task rows, inline data links and contextual entries. On task detail, the same menu exposes task-scoped actions and secondary views. Keep operations such as submit, prioritize, message, rung change, pause/pause-now, resume, take over/hand back, retry, cancel, stop and evidence export discoverable through on-demand contextual routes. Show only applicable actions and provide guidance and consequence before submission. A Role field appears only when the selected action needs a role.

The action surface is centered where the terminal geometry permits, uses `#171d25` surface, a quiet `#83bddd` edge and a clear Escape close. It lists meaningful actions for the current task. It is not a permanent button bank or a global action selector bar. Opening or navigating a menu, view or form never queues a command. Keep engine acceptance authoritative and report durable Pending, Applied or Rejected outcomes; stale escalation forms disable/reject safely without discarding entered guidance.
