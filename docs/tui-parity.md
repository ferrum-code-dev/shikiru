## 3. Terminal composition and cell mapping

The terminal has a one-cell graphite frame and compact monospace content. At the wide reference grid, map visible rows in this order:

| Order | Terminal content | Cell and layout rule |
|---:|---|---|
| 1 | Brand, project name/branch, engine state and verified uptime | One line; identity left, engine and uptime right. Uptime is unknown unless the current lock holder matches recorded start evidence. |
| 2 | Slots, running tasks, waiting tasks and integration/repository condition | One concise line from current operator projections. Keep labels once. |
| 3 | Project input+output tokens and coverage, reported API charges and missing-cost count, declared subscription-agent count | One compact line when it fits. Unknown totals stay unknown. API-equivalent estimates never appear as spend. Use “subscription agents,” never guessed accounts or plans. |
| 4 | Host CPU and RAM used/total; Shikiru CPU/RSS excluding agents; Agents CPU/RSS for this project | Three groups at wide width, wrapping by group at compact widths and separated only by ` · `. Reuse one timestamped sample and normalize process CPU to host logical-CPU capacity. Every RAM denominator is sampled host total; process RAM is RSS, not host-used RAM or a per-process limit. Preserve explicit failed, stale, unavailable and empty states when a value cannot be trusted. |
| 5 | One attention strip, always present | In healthy quiet state show `✓ No decisions needed`; say `Automation continues` only when engine-running and unblocked evidence supports it. For owned/held/stopped/faulted states, show the actual state in the quiet strip without claiming automation continues. When a decision or fault needs an action, make the strip one compact actionable row with task/project target and direct action. Do not add a second attention card or repeat its count in the summary. |
| 6 | `TASKS` with “Decision first” or an actual active count; active task rows; `Recent` completed rows | The list takes about 42% of available width. Rows are normal weight, unframed, with ID/title and concise state. Preserve current ordering rules within attention groups, stable selection and bounded history. |
| 7 | Selected task inspector | About 58% of available width, separated by one quiet vertical rule. Use the selected task's same identity and active/decision/hold state. |
| 8 | Keyboard hints and latest command feedback when relevant | One quiet footer row when height allows. Latest durable feedback sits to the right of the actions, wraps or truncates in compact layouts, and opens full history by mouse or Enter. The hidden 20×8 footer leaves command history reachable through contextual Views. Hint text may be mouse-active without becoming a permanent button row. |

The inspector order is fixed: task ID/title; state glyph and words; workflow milestone line; acting role, actual stage and elapsed value; situation; latest retained signal and recorded age; task token/charge summary with `u Details`; one role row per relevant session lineage; `e Evidence`. Rows can wrap to terminal cells. Task titles use the reference's `overflow-wrap:anywhere`: wrap rather than crop. Truncate only when required to keep a critical control reachable in the smallest pane, and keep the complete title available in inspection. Avoid extra headings and blank panels between these items. Identity, decision, ownership and every hold remain visible or immediately reachable by scrolling at compact heights.

## 4. Existing facts and necessary additive projections

Reuse the current single-writer engine, `StateReader`, bounded task queries, usage aggregation, resource sampler, task evidence and plugin contracts. Do not create a second sampler, state reader, event stream consumer, session database, preference store or engine path.

- Resource roots come from the verified engine lock identity, dashboard process, exact current-project Home/task role panes, and live role `turn.pid` identities.
