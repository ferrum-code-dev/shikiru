## 2. Composition and palette

Wide Home has a compact identity/engine/uptime header, a short operational summary, a compact project-usage line, a compact Host/Shikiru/Agents resource line, then an always-visible attention strip and the task list with selected-task inspector side by side. In a quiet project the strip says `✓ No decisions needed`; it shows an actionable item when one needs attention. The strip stays concise rather than becoming a separate attention card. The footer keeps its selection, clear, actions, detach and Help controls in order, with the latest durable command at the right. Its focusable, clickable summary includes action, target and current outcome facts, and opens full command history; on compact widths it wraps or truncates while history shows the command, its status, target and a rejection's reason. Pending shows its recorded queue timestamp; history also shows current engine state while leaving the original acknowledgement context unknown. Applied shows the engine's recorded effect, and `say` remains described as queued guidance rather than consumed guidance. Rejected shows the recorded cause. When the footer is hidden at 20×8, command history remains reachable through contextual Views.

Task 93 maps the configured header, queue, escalation, usage and resource plugins into these readouts when present. Selection updates the shared inline detail at wide and compact widths; Enter activates the focused control and does not open a duplicate task-detail screen. Views opens filters, command history, attention and each configured secondary widget. The configured widget list and shipped default remain unchanged.

Graphite background `#11151b`, surface `#171d25`, neutral border `#3d4654`, primary text `#dce2e9`, secondary text `#9aa5b5`, steel blue `#83bddd` for focus/activity, sage `#90cba6` for success/reported charges, amber `#dfb16c` for holds/decisions, and dusty rose `#e3a0a0` for errors. Names, words and width-safe glyphs identify roles/states without requiring a unique bright role color. Use restrained focus treatment, light separators and the established glyph-width policy. CLI/public renderables may retain their existing shapes where compatibility needs them.

These tokens are implemented in `ui.tokens` and registered for Textual by `ui.theme`. Task 92 applies them to the existing shell, palette, task view and evidence forms. Its shared readouts are `ProjectUsageMetric`, `ResourceMetric`, `AgentUsageRow` and `StageActivity` in `ui.compact`. They introduce no skin, theme or breakpoint setting. The retained `TaskStrip` remains available to the CLI and configured plugins; compact task detail uses words and the signal-driven one-cell activity glyph.

There are no default summary-card banks, always-visible search/filter/button bars, expanded comic strips, repeated status panels or task action toolbars. Put infrequent content/actions behind contextual navigation while keeping them discoverable and keyboard/mouse reachable.

## 3. Project readouts

Project tokens cover retained recorded session lineages, including completed tasks and earlier engine runs. State session and token coverage directly, such as `14 sessions · 412k tokens · 2 sessions without tokens`; the count is bold and a known token total is bold cyan, with coverage gaps as grey qualifiers after it; an unknown total is grey text. A recorded zero remains zero; absent reports remain unknown. Preserve legacy positive-token evidence and identify it in Details. Coverage uses the project-wide set of persisted run/session rows: explicit reports, positive legacy token evidence and unknown rows are distinguishable; totals do not imply a time window or include data whose run row is gone.

Show reported API/billed charge subtotals with explicit missing charge coverage, such as `$4.82 API · 2 costs unreported`, where the API amount is bold green and the qualifier grey. “Costs unreported” counts only declared API-mode sessions without a reported billed amount; subscription sessions with no per-task charge are excluded, and sessions with unknown billing mode are called out separately rather than treated as API charges. Do not infer monetary cost from tokens or mix actual charges and API-equivalent estimates. Estimates remain explicitly labelled in Details. A recorded zero billed amount remains a measured zero. Unknown billing modes and unavailable amounts remain explicit.

A compact subscription summary opens reported quota/window/reset observations and declared billing details. Without recorded account identities, count distinct declared subscription agents and label them as agents, not accounts or independently purchased plans. Quotas belong to the provider/account scope the plugin reports, which can include activity outside this project. Do not sum percentages across accounts or interpret a quota percentage as task completion or task cost.

The project projection reads all retained run rows through `StateReader.list_all_runs()` and is invalidated by SQLite's data version. `RecordedUsageView` carries `session_count`, token totals, `reported_sessions`, `legacy_token_sessions` and `unknown_token_sessions`, plus actual `billed_cost_usd`/coverage, API-only billed coverage, separate `api_equivalent_cost_usd`, `unknown_billing_sessions`, `subscription_sessions` and the sorted `subscription_agents`. Unknown-mode coverage is also split by its persisted source: `operator_config` means the Operator explicitly selected `unknown`, `provider_reported` means the plugin recorded an authoritative unknown, and `unknown` means the declaration was unavailable or not recorded. That last source does not establish why a historical declaration is absent. The token coverage groups are mutually distinguishable: explicit reports, positive-token legacy rows and all remaining lineages. The API missing-charge count is `api_cost_unreported_sessions`; it excludes subscription and unknown-mode runs. A billed amount reported for a non-API declaration remains in the all-mode billed subtotal and never enters the API-only subtotal.

Current-engine uptime uses lock liveness, recorded start evidence and injected `Clock`. Advance it only when the recorded start can be associated with the current lock holder; a held lock without a matching start reports `Running · uptime unknown`. A stopped engine says `Stopped` and never advances an uptime. Show a previous run duration only when its matching stop is recorded. Missing or inconsistent start/stop observations stay unknown; do not infer them from a PID, lock-file age or task timestamps. No heartbeat or uptime database is needed.

## 4. Task inspector and task view

A row presents role/current-or-previous status and agent/model together with observed tokens and declared billing mode/known charge. Do not create separate bulky Task Usage and Agents sections.

Retain each session lineage's recorded usage and historical agents after ordinary task-window/worktree cleanup. Existing session totals are cumulative and can span several same-agent models. Show recorded earlier model identities in Details, label session-wide amounts as such and do not assign a cumulative total to each model or manufacture model-level usage. A per-turn delta may be attributed only when a retained turn record names that model and contains the corresponding recorded delta; it remains a per-turn observation, not a complete model subtotal. Bounded existing turn events can supply model history; retention, interrupted turns and missing event pairs must be shown as gaps rather than an invented complete history. Never infer an earlier model from the current ladder or the run row's latest model.

Implement/plan/setup/consult/rework/integration states have compact textual stage/activity views appropriate to their actual workflow. A spinner cycles while the engine is running and the task is in progress, unheld and not stalled: a recorded current turn (including quiet tools) or the engine's own integrate/setup work, which has no agent turn; it is activity evidence, not completion percentage or engine health. Signal age remains tied to the last recorded signal. Home task status blinks under the same in-progress predicate and stays readable in every phase; waits, holds, ended turns, diagnosed stalls and stopped engines stay static. The capped motion loop refreshes primary activity from the existing strip/motion projection and incremental current-turn signal tail, including stall deadlines when animation is disabled. A slow callback does not delay other motion callbacks, and the same callback does not overlap itself. It does not reload full task evidence on motion ticks.

Details retain reported input/output/cache, monetary basis/provenance/coverage, declared billing source, reported context, quota windows/reset/observation age and session/model history. Subscription and quota observations retain their provider/account scope, which may include other projects; no combined percentage or guessed reset is shown. Task usage Details refresh reset countdowns and observation ages from the cached usage projection without loading full task evidence or process data on motion ticks. Reports/verdicts, request/ACs, engine facts, signals/timeline, blockers/relationships, workspace/role targets and export remain available through purposeful on-demand views.

`TaskDetailView.usage` carries the same coverage projection over retained task lineages. Each `TaskSessionView` keeps its persisted run identity, session-wide cumulative values, billing declaration and source, usage-report provenance, and whether the row is still live/taken over or closed. Its bounded `model_history` contains only event-recorded model/effort identities; a `usage_delta` remains an individual turn observation and does not become another session total. Its `cost_basis` is known only when the event records comparable before/after amounts on the same known basis. A basis change, missing amount, or decreasing cumulative amount leaves turn cost unknown; a legacy numeric delta without basis retains an unknown basis and never borrows the run's latest basis. Token observations remain available independently. `history_gaps` carries semantic reasons for read failures, truncated history, unlinked turns, genuinely unended starts or unavailable identity/delta evidence. New turn lifecycle events persist run ID and effort; older events without those fields are linked only when existing role/agent and recorded time evidence identifies one lineage. Ambiguous intervals remain unlinked.

## 5. Billing declarations and subscriptions

Use normalized **API**, **subscription** or **unknown** mode with an explicit source. Task 89 defines the additive contract in [04 §1](design/04-agents.md#1-contract-shikiruagentscontracts): an optional plugin capability returns `BillingDeclaration(mode, source)`, where mode is `api`, `subscription` or `unknown`, and source is `provider_reported`, `operator_config` or `unknown`. The source is `provider_reported` only for a trustworthy native report and `operator_config` only for an explicit plugin-owned option. Old plugins without that optional capability normalize to `unknown`/`unknown`. A plugin may expose a truthful report or an Operator's explicit optional declaration; absence is a documented unknown capability, not an inference from cost, model, quota, login files, credential environment or provider name. Task 90 implements the optional property and the Claude/Codex `[agents.<name>.options].billing_mode` setting.

Claude/Codex declarations remain plugin-owned and validate at their existing factory boundary. To record a choice for newly created sessions, set `billing_mode = "api"`, `"subscription"` or `"unknown"` under `[agents.<name>.options]`. An explicit `unknown` remains an explicit declaration with source `operator_config`; changing the setting applies only when a new run/session is created. An authoritative native report may instead be returned with source `provider_reported`. If a plugin accepts both, its factory validates their relationship and returns one normalized declaration; core never resolves provider-specific precedence. These fields label billing only; they do not select provider access, alter authentication, inject secrets or introduce a tariff table. Task 90 persists the fields per run/session and exposes them in task session details and evidence export.

Persist the declaration/source with the run/session it describes, captured when that run starts. The additive `runs.billing_mode` and `runs.billing_source` fields are run-scoped session facts written by the engine's single writer; a resumed or model-changed session keeps its original declaration. Existing rows and sessions without a reliable declaration migrate to `unknown`/`unknown`. Changing current configuration must not retroactively relabel historical runs. Keep billing mode distinct from `billed`, `api_equivalent` and `unknown` monetary evidence, and preserve reported amounts/unknowns without interpreting subscription mode as a measured zero.

A subscription row shows tokens and `Subscription`; reported quota/reset details show how close the account is to a limit. The Project usage popup keeps sessions with unknown billing mode (`unknown`) separate from API sessions whose charge was not reported (`API unreported`) in its Billing row; raw billing sources are not shown there. A fixed plan fee belongs to an account/time period, not to each task. This phase adds no account manager, billing integration, guessed plan fee or per-task fee allocation. A reliable separately reported task charge can still be shown with its source. No charge is manufactured from an API-equivalent estimate.

## 6. Navigation and operator control

If no decision is open, the list keeps its existing selection behavior. The task details list (06 §5) replaces the task Views selector and Open control: arrows and Enter open a section, the project entries follow the nine sections, and Esc closes. Task details puts quiet metadata (mode, submitted/requeued age, dispatch priority, status reason and project attention counts) on demand; current status, critical decisions, ownership and every hold remain in the task summary.
