## 2. Composition and palette

Wide Home has a compact identity/engine/uptime header, a short operational summary, a compact project-usage line, a compact host/instance resource line, an actionable attention row when required, then task list and selected-task inspector side by side. A quiet project does not require a permanent attention panel. The bottom shows concise keyboard hints and command feedback when relevant.

Task 93 maps the configured header, queue, escalation, usage and resource plugins into these readouts when present. At compact widths the Home task list remains primary and Enter opens the selected task in the existing shared detail screen; at usable wide sizes the selected inspector sits beside the list. Views opens filters, command history, attention and each configured secondary widget. The configured widget list and shipped default remain unchanged.

Graphite background `#11151b`, surface `#171d25`, neutral border `#3d4654`, primary text `#dce2e9`, secondary text `#9aa5b5`, steel blue `#83bddd` for focus/activity, sage `#90cba6` for success/reported charges, amber `#dfb16c` for holds/decisions, and dusty rose `#e3a0a0` for errors. Names, words and width-safe glyphs identify roles/states without requiring a unique bright role color. Use restrained focus treatment, light separators and the established glyph-width policy. CLI/public renderables may retain their existing shapes where compatibility needs them.

These tokens are implemented in `ui.tokens` and registered for Textual by `ui.theme`. Task 92 applies them to the existing shell, palette, task view and evidence forms. Its shared readouts are `ProjectUsageMetric`, `ResourceMetric`, `AgentUsageRow` and `StageActivity` in `ui.compact`. They introduce no skin, theme or breakpoint setting. The retained `TaskStrip` remains available to the CLI and configured plugins; compact task detail uses words and the signal-driven one-cell activity glyph.

There are no default summary-card banks, always-visible search/filter/button bars, expanded comic strips, repeated status panels or task action toolbars. Put infrequent content/actions behind contextual navigation while keeping them discoverable and keyboard/mouse reachable.

## 3. Project readouts

Project tokens cover retained recorded session lineages, including completed tasks and earlier engine runs. State reported/unknown session coverage directly, such as `412k tokens · 12/14 sessions`. A recorded zero remains zero; absent reports remain unknown. Preserve legacy positive-token evidence and identify it in Details. Coverage uses the project-wide set of persisted run/session rows: explicit reports, positive legacy token evidence and unknown rows are distinguishable; totals do not imply a time window or include data whose run row is gone.

Show reported API/billed charge subtotals with explicit missing charge coverage, such as `API $4.82 · 2 costs unreported`. “Costs unreported” counts only declared API-mode sessions without a reported billed amount; subscription sessions with no per-task charge are excluded, and sessions with unknown billing mode are called out separately rather than treated as API charges. Do not infer monetary cost from tokens or mix actual charges and API-equivalent estimates. Estimates remain explicitly labelled in Details. A recorded zero billed amount remains a measured zero. Unknown billing modes and unavailable amounts remain explicit.

A compact subscription summary opens reported quota/window/reset observations and declared billing details. Without recorded account identities, count distinct declared subscription agents and label them as agents, not accounts or independently purchased plans. Quotas belong to the provider/account scope the plugin reports, which can include activity outside this project. Do not sum percentages across accounts or interpret a quota percentage as task completion or task cost.

The project projection reads all retained run rows through `StateReader.list_all_runs()` and is invalidated by SQLite's data version. `RecordedUsageView` carries `session_count`, token totals, `reported_sessions`, `legacy_token_sessions` and `unknown_token_sessions`, plus actual `billed_cost_usd`/coverage, API-only billed coverage, separate `api_equivalent_cost_usd`, `unknown_billing_sessions`, `subscription_sessions` and the sorted `subscription_agents`. The token coverage groups are mutually distinguishable: explicit reports, positive-token legacy rows and all remaining lineages. The API missing-charge count is `api_cost_unreported_sessions`; it excludes subscription and unknown-mode runs. A billed amount reported for a non-API declaration remains in the all-mode billed subtotal and never enters the API-only subtotal.

Current-engine uptime uses lock liveness, recorded start evidence and injected `Clock`. Advance it only when the recorded start can be associated with the current lock holder; a held lock without a matching start reports `Running · uptime unknown`. A stopped engine says `Stopped` and never advances an uptime. Show a previous run duration only when its matching stop is recorded. Missing or inconsistent start/stop observations stay unknown; do not infer them from a PID, lock-file age or task timestamps. No heartbeat or uptime database is needed.

## 4. Task inspector and task view

Use the same compact task presentation in Home and `dash --task`: full reachable ID/title, state/current stage, all holds/ownership, meaningful activity/decision, a short task usage total, then combined agent/usage rows. A row presents role/current-or-previous status and agent/model together with observed tokens and declared billing mode/known charge. Do not create separate bulky Task Usage and Agents sections.

Retain each session lineage's recorded usage and historical agents after ordinary task-window/worktree cleanup. Existing session totals are cumulative and can span several same-agent models. Show recorded earlier model identities in Details, label session-wide amounts as such and do not assign a cumulative total to each model or manufacture model-level usage. A per-turn delta may be attributed only when a retained turn record names that model and contains the corresponding recorded delta; it remains a per-turn observation, not a complete model subtotal. Bounded existing turn events can supply model history; retention, interrupted turns and missing event pairs must be shown as gaps rather than an invented complete history. Never infer an earlier model from the current ladder or the run row's latest model.

Implement/plan/setup/consult/rework/integration states have compact textual stage/activity views appropriate to their actual workflow. A signal spinner is activity evidence, not completion percentage or engine health. The capped motion callback refreshes primary activity from the existing strip/motion projection and incremental current-turn signal tail, including stall deadlines when animation is disabled; disabled animation keeps the signal glyph static. It does not reload full task evidence on motion ticks.

Details retain reported input/output/cache, monetary basis/provenance/coverage, declared billing source, reported context, quota windows/reset/observation age and session/model history. Subscription and quota observations retain their provider/account scope, which may include other projects; no combined percentage or guessed reset is shown. Task usage Details refresh reset countdowns and observation ages from the cached usage projection without loading full task evidence or process data on motion ticks. Reports/verdicts, request/ACs, engine facts, signals/timeline, blockers/relationships, workspace/role targets and export remain available through purposeful on-demand views.

`TaskDetailView.usage` carries the same coverage projection over retained task lineages. Each `TaskSessionView` keeps its persisted run identity, session-wide cumulative values, billing declaration and source, usage-report provenance, and whether the row is still live/taken over or closed. Its bounded `model_history` contains only event-recorded model/effort identities; a `usage_delta` remains an individual turn observation and does not become another session total. Its `cost_basis` is known only when the event records comparable before/after amounts on the same known basis. A basis change, missing amount, or decreasing cumulative amount leaves turn cost unknown; a legacy numeric delta without basis retains an unknown basis and never borrows the run's latest basis. Token observations remain available independently. `history_gaps` carries semantic reasons for read failures, truncated history, unlinked turns, genuinely unended starts or unavailable identity/delta evidence. New turn lifecycle events persist run ID and effort; older events without those fields are linked only when existing role/agent and recorded time evidence identifies one lineage. Ambiguous intervals remain unlinked.

## 5. Billing declarations and subscriptions

Use normalized **API**, **subscription** or **unknown** mode with an explicit source. Task 89 defines the additive contract in [04 §1](design/04-agents.md#1-contract-shikiruagentscontracts): an optional plugin capability returns `BillingDeclaration(mode, source)`, where mode is `api`, `subscription` or `unknown`, and source is `provider_reported`, `operator_config` or `unknown`. The source is `provider_reported` only for a trustworthy native report and `operator_config` only for an explicit plugin-owned option. Old plugins without that optional capability normalize to `unknown`/`unknown`. A plugin may expose a truthful report or an Operator's explicit optional declaration; absence is a documented unknown capability, not an inference from cost, model, quota, login files, credential environment or provider name. Task 90 implements the optional property and the Claude/Codex `[agents.<name>.options].billing_mode` setting.

Claude/Codex declarations remain plugin-owned and validate at their existing factory boundary. An optional `billing_mode` setting belongs under that plugin's `[agents.<name>.options]` table; when supplied, the factory returns it with source `operator_config`. An authoritative native report may instead be returned with source `provider_reported`. If a plugin accepts both, its factory validates their relationship and returns one normalized declaration; core never resolves provider-specific precedence. These fields label billing only; they do not select provider access, alter authentication, inject secrets or introduce a tariff table. Task 90 persists the fields per run/session and exposes them in task session details and evidence export.

Persist the declaration/source with the run/session it describes, captured when that run starts. The additive `runs.billing_mode` and `runs.billing_source` fields are run-scoped session facts written by the engine's single writer; a resumed or model-changed session keeps its original declaration. Existing rows and sessions without a reliable declaration migrate to `unknown`/`unknown`. Changing current configuration must not retroactively relabel historical runs. Keep billing mode distinct from `billed`, `api_equivalent` and `unknown` monetary evidence, and preserve reported amounts/unknowns without interpreting subscription mode as a measured zero.

A subscription row shows tokens and `Subscription`; reported quota/reset details show how close the account is to a limit. A fixed plan fee belongs to an account/time period, not to each task. This phase adds no account manager, billing integration, guessed plan fee or per-task fee allocation. A reliable separately reported task charge can still be shown with its source. No charge is manufactured from an API-equivalent estimate.

## 6. Navigation and operator control

Click a row or use Up/Down to select a task; Enter inspects it and Escape returns to the same selection. `Ctrl+P` opens the selected task's contextual action menu; its primary actions include direct Answer, Inspect, Evidence & reports, Message, applicable Take over/Hand back, Usage, Commands and Project diagnostics. More actions exposes remaining task/project operations. `e` opens Evidence, `u` opens Usage Details and `v` remains the contextual Views route for filters, history and secondary views; `?` opens help. Views and Help are also mouse reachable. Opening or navigating a route does not dispatch a command. Search starts hidden in Home; `/` shows and focuses it, Enter moves to the results, and Escape clears a nonempty search before hiding the empty input. Contextual filters/history and secondary views preserve task identity, list search, reading position and focus. Native form inputs retain text-entry keys. In a task inspector, the keyboard and Views selector open the same on-demand sections; task window and role-pane targets stay available there.

Use the existing palette/forms and `OperatorCommands`, not widget-created commands. Keep all operations discoverable, including submit, prioritize, message, rung change, pause/pause-now, resume, take over/hand back, retry, cancel, stop and export. Show timing and consequences, applicable/disabled actions and durable Pending/Applied/Rejected outcomes. Queueing a message is not consumption by an agent.

Task detail Views uses one task-scoped selector and an Open control for its sections, Operator actions, Help and configured secondary widgets. Task details puts quiet metadata (mode, submitted/requeued age, dispatch priority, status reason and project attention counts) on demand; current status, critical decisions, ownership and every hold remain in the task summary. The selector and action form scroll within short panes, and the palette retains its existing task and role context.

Decision/ownership/hold information remains visible without multiple competing panels. Missing escalation evidence does not hide its durable question/allowed actions. Another Operator's resolution disables a stale form and preserves guidance; engine revalidation remains authoritative. Navigating or inspecting must not mutate workflow state or recreate completed-task resources.

Short panes reduce summary height and scroll focused content into view. Never compress a wide inspector into unreadable columns or silently hide a critical decision, task identity, hold, input or result control.

Verify wide Home/task/form panes, 48 and 36 columns, short and very small panes, `NO_COLOR`, `TERM=dumb` and disabled motion. Respect the existing glyph-width policy and fixed named layout limits; do not add speculative layout/skin settings or automatically rearrange tmux splits. Text/markers retain state, ownership, focus and result meanings without color or movement.

Task 95 keeps the Home split only at 100 columns or wider and above 18 rows. Below that threshold the task browser is the primary Home surface; Enter opens the selected task and Escape returns to the same selection. Primary rows keep their ID and a concise state line, ellipsizing long text; the complete title, decision, ownership and holds remain in task detail. Task identity, ownership and command feedback scroll with the task body so they remain reachable in short panes. The verified 20×8 layout requires keyboard navigation and scrolling for longer details/forms; comfortable text entry needs more rows. Widths below 20 columns and ambiguous-width CJK terminal settings are not verified.

Search, filters, History, configured widget order and task/role context keep their existing routes. Resizing, row reordering and state refresh preserve task identity, focus, form contents and intended task-body reading position. Disabling animation leaves its glyph static while existing state and data refresh cadence continues; it does not add a polling source. ## 8. Architecture and configured plugins

Domain rules stay pure; SQL stays in store; plugin-specific behavior stays in agent plugins; processes/time use injected runners/clocks; wiring stays in bootstrap. Reuse operator queries, usage aggregation, subscriptions, command history, retained evidence and the existing resource sampler. Add bounded consumed projections and compatible widget-contract fields, not another scheduler/reader/stream consumer or preference database.


The compact resource line has **Host** CPU/RAM and **Shikiru including agents** CPU/RAM. Instance measurements use the existing deduplicated engine and project-pane process trees, including agent descendants found in those trees; no separate agent resource item is shown. Host CPU is the existing windowed average, host RAM is the observed host reading, and instance CPU/RSS are the same sample's process-tree measurement. Keep the sample timestamp and age. An empty process tree is not measured zero; preserve failed, stale, unavailable and empty distinctions in Details and show explicit state when a primary value cannot be trusted. Do not sum host and instance measurements or resample on motion ticks.

Task 91 exposes the existing resource snapshot through `DashboardViews.resource_sample()` without sampling again. A recent failed process-tree sample remains failed or stale with its error and keeps the last complete snapshot's original timestamp; only a new complete sample clears that failure. A missing first observation remains unavailable to the consumer, while a failed first attempt is explicitly failed. Empty process trees retain absent instance CPU/RSS rather than becoming zero.

Existing widget names, entry points and callbacks remain stable. The existing `dashboard.widgets` list and its shipped default are unchanged; no configuration migration rewrites an Operator's chosen order or removes a widget. Task 93 maps `header` to compact identity/engine status, `queue` to the Home task list, `escalations` to a conditional actionable attention row, `usage` to the compact project usage readout, and `resources` to the compact host/instance line. The compatible `WidgetContext.home_attention_present` flag tells identity widgets when the Home attention row already carries fault/escalation context, so legacy alert context stays visible when that row is absent without duplicating the default row. `strips` remains reachable as a secondary workflow view and is not in the primary Home composition. `dialogue` remains in Activity; `docker` and `faults` remain in Diagnostics; command history, detailed usage, reports, relationships and export remain reachable from contextual views. Every configured third-party widget stays in Extensions in configured relative order with its existing entry point and callbacks. The optional widget placement capability is declared through `dashboard.contract`; an extension with no placement capability defaults to Extensions. Missing or broken configured plugins continue to fail validation by name and are never silently hidden. Each implementation task documents only the compatible fields it consumes.

Remove superseded private presentation as screens convert. Preserve useful public CLI/plugin contracts and all workflow services. Necessary responsibility-splitting refactors are separate commits, not a speculative framework.
