# Shikiru — Agent Conventions

- **Read first**: `docs/design.md`.
- **Conventions**: SOLID, KISS, YAGNI. One responsibility per class; pure functions in `domain`; constructor injection; no comments, clear names; docstrings only on public contracts and their implementations. No literals: tunables go in `defaults.toml`, protocol values in named constants. No silent fallbacks, no bare `except`. Build nothing beyond the task.
- **Tests**: behaviour over implementation. Unit tests only for `domain` rules, models and parsers; integration tests for the rest (real SQLite, git, tmux via `tmux_server`, fake agent). Wait with `wait_until`, time with `FakeClock`, never sleep. No mocks of our own classes, no snapshot spam. Coverage ≥ 80%.
- **Test value**: test domain rules and invariants, not the framework or data shape — no tests for pydantic features (frozen, extra, defaults), enum or constant listings, trivial wiring, or message/description wording. One table per rule. Integration tests assert observable behaviour at boundaries; coverage beyond the gate is not a goal.
- **Environment**: In each fresh worktree run `uv sync --locked`. Verify that Python imports and tool entrypoints resolve to this worktree. If a copied `.venv` points elsewhere, recreate it before verification.
- **Verification**: Match checks to the change. For documentation-only changes, including agent instructions, review the diff and run `git diff --check`; do not run application tests. For code or executable configuration changes, run relevant checks while developing, then `PYTEST_ADDOPTS='--dist=loadfile' uv run poe check` (the local worker count is half the CPU cores unless `SHIKIRU_TEST_CPUS_PER_WORKER` overrides the divisor; CI pins `-n` per OS in `ci.yml`, so do not pass `-n` locally) on the final changes before the final commit and completion report; it must be green. Repeat the full gate only when subsequent changes invalidate that result.
- **Execution**: Prefer foreground checks. For background commands, retain their process handle and log path, inspect their exit status, and check existing results when resuming. Do not rely solely on completion notifications or start duplicate checks.
- **Commits**: Conventional commits, one coherent change each. Separate independent refactorings; keep small supporting refactorings with the behavior they enable. The subject is what the release notes show, so write it for a user: `type(scope): what changed`. A change that breaks behavior, configuration or the schema marks the type with `!` or adds a `BREAKING CHANGE:` line to the body.
